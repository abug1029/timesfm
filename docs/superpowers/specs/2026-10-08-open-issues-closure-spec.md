且它已覆盖 "supervisor down"（S1），比只查心跳更全。

#### 4.1.2 调度（【建议】）

- **落点**：Windows Task Scheduler 每 **15** 分钟调 WSL 跑一次
  （比纯 shell 循环抗 WSL 重启）；备选 systemd timer
- **调度间隔与心跳阈值的关系**：`HB_AGE > 12` 判死亡 + 15 分钟调度间隔
  ⇒ 实际最坏恢复时延 ≈ 12 + 15 = **27 分钟**（不是 12 分钟，见 §1.2 修正）

#### 4.1.3 维护窗口旗标（【建议】新增，**须带过期**）

`data/cache/maintenance.flag` 存在时脚本**只报状态、不执行自愈**。
现有 `diagnose_three_loop.sh` 无此保护，人工部署期间可能被它 SIGTERM。

**⚠️ 旗标必须有过期机制**，否则"忘删旗标"会使自愈**永久失效** ——
这是本方案最可能的人为事故（比不装看门狗更糟，因为故障不可见）：

| 规则 | 【建议】取值 | 说明 |
|---|---|---|
| 过期判据 | 旗标 **mtime > T_expire** 即失效 | 用 mtime 而非内容，避免写入方漏填时间 |
| T_expire | **4 小时** | 覆盖一次常规部署；更长的维护须续期（`touch` 即可） |
| 过期行为 | **自动视为不存在，自愈恢复执行**，日志留 `flag expired` 事件 | fail-safe 方向选"恢复自愈"，不是"继续禁用" |
| 忘删检测 | 过期事件走 Q4 告警通道 | 让"忘了删"被看见而不是静默 |
| 未过期时 | 只报状态，**不执行自愈**，日志留 `maintenance active` | 与初稿一致 |


#### 4.1.4 孤儿扫尾挂钩（【建议】）

在 `diagnose_three_loop.sh` 的自愈分支里、执行 `start_supervisor.sh` **之前**插入扫尾，
见 §4.2。

#### 4.1.5 反复自愈的熔断（【建议】新增）

**Q4 只解决"失败要告警"，不解决"反复失败"**。若 `start_supervisor.sh` 连续失败，
每次调度都会再试 → **重启风暴**（反复 SIGTERM + 拉起，比单次故障更难诊断）。

| 规则 | 【建议】取值 | 说明 |
|---|---|---|
| 连续失败计数 | `data/cache/heal_fail.count`；一次成功自愈即清零 | 只计"拉起后又立刻死"的情况 |
| 熔断阈值 | **连续 3 次** | 3 次仍失败基本是环境问题（PATH / 依赖缺失），不是偶发 |
| 熔断动作 | **停止自动自愈**，置 `STATE=NEEDS_HUMAN` + 走 Q4 告警 | 复用脚本既有 `NEEDS_HUMAN` 分支 |
| 解除 | 人工删计数文件；或 **T_cooldown = 30 分钟**后自动半开一次 | 半开 = 试一次，成功即恢复 |
| 退避 | 未熔断时也按 **1× → 2× → 4×** 递增 | 避免短周期反复 SIGTERM |

**旗标过期、熔断、扫尾、调度四件事必须同批实施** ——
否则"装了看门狗"会引入一个比原来更难诊断的故障模式。

### 4.2 D5 孤儿 run 回收（【建议】）

#### 4.2.1 先摆清三套既有机制（避免造第四套）

| 机制 | 位置 | 作用 | 触发 |
|---|---|---|---|
| **flock 判活** | `:3158-3167` `aligned_slow_loop.lock` + `fcntl.flock(LOCK_EX\|LOCK_NB)` | 慢环**是否真在跑**（持锁即在跑） | 监督环查询时 |
| **按批次清理** | `:4102` `cleanup_batch_workers(batch_id)`，`:4231` 调用 | 按 `--batch-id` 做 `pkill`，收本批次 worker | 批次结束时 |
| **退出不杀子进程** | `:696` `_shutdown_exit()` docstring：「不收割，不启动新 run，**不杀已经在跑的子进程**」 | 干净退出时**刻意不**收子进程 | 信号退出 |

**⚠️ 合同冲突**：`active_runs.json` 方案若在正常退出时 SIGTERM 子进程，
就是**改写 `:696` 这条既有合同**，不是"补一个空函数"。该合同设立的理由
未记录在代码里，须在裁定前确认（Q8）。

#### 4.2.2 三套机制的归属（【建议】）

`active_runs.json` 会成为**第三套 run 登记**，必须先定它与 flock、与批次清理的关系：

| 问题 | 【建议】 |
|---|---|
| flock 与 `active_runs.json` 谁说了算？ | **flock 优先**。它是内核级事实（持锁 = 真在跑）；json 是监督环的**记账**，可能与事实不符。扫尾时**以 flock 判"该不该杀"，以 json 判"该杀哪个 pid"** |
| `cleanup_batch_workers` 是否重复？ | **不重复**，分工不同：它收本批次 worker（正常路径）；json 扫尾收**跨实例遗留** run（异常路径）。两者按 pid 去重 |
| 是否改 `:696` 合同？ | **【建议】不改**，见 4.2.3 路线 A |

#### 4.2.3 回收路线（【待决】Q8）

| 路线 | 做法 | 影响 |
|---|---|---|
| **A. 只做硬杀兜底**（【建议】） | 不动 `:696`；只在自愈脚本重启**前**扫尾 `active_runs.json` | 正常退出仍不杀子进程（合同不变）；硬杀场景 ≤1 个调度间隔才回收 |
| B. 改 `:696` 合同 | 干净退出时也 SIGTERM | 需先确认该合同设立理由；且**只覆盖正常退出**，OOM/段错误仍不触发 |
| C. 两者都做 | B + A | 最彻底，但合同变更风险最大 |

**【建议】A**：路线 B 补不上硬杀路径的洞（OOM 不走退出钩子），
却要动一条理由不明的既有合同——收益/风险比不划算。

#### 4.2.4 记账与防误杀（路线 A 下的具体做法）

**⚠️ 两段式写入 —— 否则存在"孤儿无记录"的竞态窗口**

初稿写「`Popen` 之后立即写入 pid」。若 supervisor 恰在 **`Popen` 与写入之间**被硬杀，
子进程已生、记录未落 → **这正是本项要消灭的孤儿，却在它诞生的瞬间不可见**。
竞态窗口很窄，但 D5 的存在理由就是覆盖"任意时刻被杀"，窄窗口同样漏：

| 阶段 | 时机 | 写入内容 |
|---|---|---|
| **① 意图** | `Popen` **之前** | `intent`：`batch_id` + 提案上下文 + 启动时刻（**无 pid**）→ 原子落盘 |
| **② 回填** | `Popen` 成功后 | 该 `intent` 补 `pid`，转正式记录 |
| **③ 清理** | 批次结束 / 正常退出 | 删除对应条目 |

- **扫尾位置**：`diagnose_three_loop.sh` 自愈分支内、调 `start_supervisor.sh` **之前**
- **遇到无 pid 的 `intent`**（① 已写、② 未回填即被杀）：子进程可能已生，
  **以 flock + `/proc` 进程树反查定位**；查不到则仅清该 `intent`
- **防误杀**：记录 `pid` + 进程创建时刻（Linux `/proc/<pid>/stat` 第 22 字段），pid 复用时跳过
- **清空**：确认 kill 后删除对应条目，避免下次重复扫

**判据不一致时谁在前**（flock 与 json 打架的两种情形）：

| 情形 | 含义 | 处置 |
|---|---|---|
| json 有 pid，但 **flock 显示未持锁** | 记账在、进程不在（或 pid 已被复用） | **不杀**，直接清条目 |
| **flock 持锁**，但 json 无对应 pid | 记账丢失（竞态 / 写盘失败），进程真在跑 | **杀**，pid 由 `/proc` 反查 |
| 两者一致 | 正常 | 按 json 的 pid 条目处置 |

**结论**：**flock 是权威**（内核事实），json 只是"杀哪个 pid"的线索；
不一致时**一律以 flock 定性** —— 这是 §4.2.2「flock 优先」的具体落地，
也回答了"pid + 创建时刻"与"flock 判该不该杀"谁在前：**flock 先定性，pid 后定位**。

**回滚的总原则**：**每项变更都必须能退回到"本次变更之前"的状态，

### Q10 — M3 拒收统计窗口（**M3 的开工门槛**）

**硬约束**（`specs/2026-10-03-peer-memory-loop-closure-spec.md`）：

> `:82` —— 计数必须来自 `.omc/supervisor_decisions.jsonl` 里**本轮**的记录，
> **这样重启后还能渲染出同一份摘要**。本文件不定义「本轮」的起止。
> 在宿主写下窗口之前，**不实现这一节**。
>
> `:172` —— **「在这句被宿主写成可检查的起止条件之前，D1 不开始」**。

#### ⚠️ 初稿的「近 7 天」是错方案

滚动时间窗 = `f(当前时刻)`。同一份日志在 T 与 T+1min 渲染出**不同**摘要 ——
**直接违反幂等要求**。仓内同类硬约束见 `:2585`：
「不含墙钟，保证除 `generated_at` 外物化幂等」。

**所以合法方案只有一个形态**：窗口必须是**可检查的固定起止条件**，
而非滚动时间窗。

| 选项 | 形态 | 取舍 |
|---|---|---|
| (a) **本次 supervisor 进程启动至今** | 起点可从 `supervisor_state.json` 推出 | **【建议】**。天然满足幂等：supervisor 重启即开新轮，重启后渲染的是新轮摘要，逻辑自洽 |
| (b) 显式时间戳 | 宿主指定（如某次部署时刻） | 同样幂等，但需人工维护 |
| (c) 日志中某标记事件之后 | 依赖日志结构 | 需先确认日志有无稳定标记 |

**这需要宿主给出一个可检查的定义。给不出，M3 就不能开工。**

#### ⚠️ 选项 (a) 与 D4 自愈的交互副作用（初稿未讨论）

选项 (a) 意味着 **每次 supervisor 重启即开新轮 → 拒收统计清零**。
而 **D4 自愈恰恰会让重启变频繁**（心跳停更即 SIGTERM + 拉起），
于是出现**自伤耦合**：

> 自愈越灵敏 → 重启越多 → M3 的拒收统计被反复抹掉 → peer 看到的
> 「最近拒收分布」信息量越低。

三选项的耦合程度：

| 选项 | 重启是否清零 | 与 D4 的耦合 | 评价 |
|---|---|---|---|
| (a) 进程启动至今 | **是** | **强**（重启即清） | 幂等最自然，但被 D4 削弱 |
| (b) 显式时间戳 | 否 | **弱**（重启不清） | 需人工定，但不受自愈影响 |
| (c) 标记事件之后 | 否 | 弱 | 依赖日志标记是否存在 |

**【建议】的折中**：**主窗口用 (a)**（保幂等），**另附一个跨轮累计的对照段**
（`累计 since <marker>`，只读不参与渲染决策），使"被重启抹掉"可被看见而非静默丢失。
