# Laya 服务优化专家调研报告

**日期：** 2026-11-07  
**调研团队：** perf-expert, arch-expert, sys-expert

---

## 📊 核心发现

**根本原因已确认：单线程推理队列导致的请求堆积**

| 指标 | 数值 |
|------|------|
| 总请求数 | ~14,750 |
| 成功率 | **17.1%** (2,516 成功 / 12,234 被拒) |
| 中位推理时间 | 16.5秒 |
| 中位总耗时 | 103秒 |
| 中位排队等待 | **86秒** |
| 客户端超时阈值 | ~240秒 |

**时间差异解释：**
- 推理时间：~17秒（实际模型计算）
- 总耗时：230-288秒 = 17秒推理 + **213-271秒排队等待**

---

## 🔍 三位专家的核心结论

### 1️⃣ 性能专家 (perf-expert)

**瓶颈定位：**
- **主因：** `ThreadPoolExecutor(max_workers=1)` - 单推理线程
- **次因：** uvicorn 单 worker 进程
- **误解澄清：** `LAYA_THREADS=4` 只控制 PyTorch 内部线程，不是请求并发数

**关键代码：**
```python
# serve.py:1079
pool = ThreadPoolExecutor(max_workers=1, thread_name_prefix="laya-infer")
```

**优化建议（按优先级）：**
1. **增加推理线程池** → `max_workers=4` (预期 handler 从 103s 降至 25-30s)
2. **降低 MAX_CONCURRENT** → 从 16 降至 4-8，匹配推理能力
3. **启用 uvicorn 多 worker** → 需测试内存限制
4. **添加请求超时** → 120秒快速失败，释放队列槽位

---

### 2️⃣ 架构专家 (arch-expert)

**当前架构三层控制：**
| 层级 | 机制 | 行为 |
|------|------|------|
| 准入层 | `Semaphore(16)` | 允许16个并发，满时返回503 |
| 推理门 | `asyncio.Lock()` | 全局排他锁，一次一个推理 |
| 工作池 | `ThreadPoolExecutor(1)` | 单线程执行 |

**方案对比：**

| 方案 | 难度 | 内存 | 吞吐提升 | 推荐度 |
|------|------|------|----------|--------|
| **A. 请求队列** | 低 | 无 | 中 (减少503) | ⭐⭐⭐⭐⭐ |
| **B. 多 Worker + 读写锁** | 中 | 无 | 高 (2-4x) | ⭐⭐⭐⭐ |
| C. uvicorn --workers | 低 | 高 | 高 | ❌ (6GB RAM不足) |
| D. 反向代理+多实例 | 高 | 高 | 极高 | ⭐⭐⭐ (长期) |
| E. Celery异步队列 | 高 | 中 | 低 | ❌ (不适用) |

**推荐方案 A（首选）：**
```python
# 改为排队等待而非立即拒绝
try:
    await asyncio.wait_for(admission.acquire(), timeout=30)
except asyncio.TimeoutError:
    raise HTTPException(status_code=503, ...)
```

---

### 3️⃣ 系统专家 (sys-expert)

**超时链路分析：**
```
Client --[240s超时]--> Laya :8000
                         |
                   [FIFO队列，单线程]
                         |
                   位置9+的请求 > 240s → 客户端断开
```

**关键发现：**
- 客户端超时 ~240秒（可能是云平台/防火墙/HTTP库设置）
- 队列位置 9 的请求：等待 162s + 推理 18s = 180s（接近超时）
- 队列位置 13+ 的请求：必定超时断开

**优化建议：**
1. **服务端：** 实现异步响应模式（返回任务ID，客户端轮询）
2. **反向代理：** 如使用 nginx，设置 `proxy_read_timeout 300s`
3. **客户端：** 调整 HTTP 库超时设置至 300秒+
4. **快速失败：** 预估等待时间，超过 180秒直接返回 503 + `Retry-After`

## 🎯 综合优化方案（实施路线图）

### 阶段一：快速修复（1-2天）

**目标：** 将成功率从 17% 提升至 50%+

1. **增加推理线程池**
   ```powershell
   $env:LAYA_INFERENCE_WORKERS = '4'
   ```
   修改 `serve.py:1079` 读取环境变量

2. **调整并发限制**
   ```powershell
   $env:LAYA_MAX_CONCURRENT = '6'  # 匹配推理能力
   ```

3. **添加排队机制**（替代立即503）
   ```python
   # 排队等待，超时后返回
   await asyncio.wait_for(semaphore.acquire(), timeout=60)
   ```

**预期效果：**
- 成功率：17% → 50-60%
- 平均响应时间：103s → 30-40s
- 客户端超时断开：减少 70%

---

### 阶段二：中期优化（1-2周）

**目标：** 成功率 80%+，支持更高并发

1. **实现读写锁**（替代全局排他锁）
   - 多个 predict 可并行（读锁）
   - checkpoint 加载/卸载需排他（写锁）

2. **添加监控指标**
   - 实时队列深度
   - 推理槽位利用率
   - 预估等待时间

3. **实现预估快速失败**
   ```python
   estimated_wait = queue_depth * avg_inference_time
   if estimated_wait > 180:
       return 503, Retry-After: 30
   ```

---

### 阶段三：长期架构（1-2月）

**目标：** 支持 10x 并发，企业级可靠性

1. **异步任务队列**
   ```
   Client --提交--> Queue --返回任务ID--> Client
                     |
                  Worker Pool (4-8 workers)
                     |
                  Client --轮询结果--> /tasks/{id}
   ```

2. **多实例 + 负载均衡**（需升级硬件至 16GB+ RAM）
   ```
   nginx (LB) --> Laya Instance 1 (:8001)
                --> Laya Instance 2 (:8002)
                --> Laya Instance 3 (:8003)
   ```

3. **GPU 加速**（如可行）
   - 推理时间：17s → 1-2s
   - 根本解决性能瓶颈

## 💡 关键洞察

**三位专家的一致结论：**

1. **性能瓶颈不在推理，在排队** - 17秒推理变成 288秒是因为前面有 15 个请求在等
2. **立即 503 比长时间等待更糟** - 客户端体验差，且浪费已消耗的计算资源
3. **硬件限制是根本约束** - 6GB RAM 限制了多进程/多实例方案
4. **异步模式是最终答案** - HTTP 长连接不适合分钟级任务

**推荐立即实施方案一（快速修复），可在 1-2 天内显著提升服务质量。**
