### 裁决理由

1. 写入方唯一 + 第三套语义已退役 ⇒ 改名收益低；改名成本高（历史裁决行迁移 + 读点改造）。**(b) 正确**。
2. 指纹判断成立：改名与否均不动 `protocol_fingerprint`，无 bump 风险。
3. 守卫实施与 Q2=(b) 的键名要求一致（守卫查现有 `tier`）。

### 勘误（重要）：「值域守卫防止第三套语义混入」声明不成立

- **归档代码实测**：`two_star_critic.py:37-39` 的 `TIER_A = {"fu","rb","fg","ta","lh"}` / `TIER_B` / `TIER_C` 是**品种集合常量**（作业优先级分组），既不是批次 B 提交所称的 `1/2/3`，也不直接是调研 spec 所称的写入 verdict 的 `"A"/"B"/"C"` 字面值——**两处描述互不一致，且均系对归档代码的不精确转述**。
- **技术事实**：若真有人把组名 `"A"` 写入 `verdict["tier"]`，`"A" ∈ {S,A,B,C,D}`，`is_valid_tier()` 放行 → 仍被静默当作变体级 A。值域守卫真正挡住的是**第二套语义（中文值）、`None`、数字**等非法值。
- **第三套语义的实际防线**是「写入方唯一 + two_star_critic 已退役且其本身从不写 verdict」这一结构性事实，而非值域。
- **处置**：`is_valid_tier()` docstring 与调研 spec §4.2.1 勘误措辞（守卫防的是「非法值」，第三套语义防线是写入方唯一性）。风险评级：低——退役脚本本就不在写入路径上，但须防止后人误信已有值域防线而放松写入方唯一性约束。

## 3. Q7 — `diagnose_three_loop.sh` 定位：维持 (a) 收编；附两项须处置偏离

### 事实核验

| 调研 spec 声明 | 核验结果 |
|---|---|
| 收编为唯一自愈入口 | ✓ 批次 A `6ca6d8d` 在 `diagnose_three_loop.sh` 内实现（+105 行），S1-S4 四分支保留，无第二支看门狗 |
| 熔断阈值连续 3 次 | ✓ `CIRCUIT_BREAKER_THRESHOLD=3`；成功清零 + `d5_disabled.flag` 联动 + 删计数文件恢复 |
| 维护窗口旗标须带过期 | ⚠ **偏离**：实施 `MAINT_FLAG_EXPIRE_DAYS=7`，closure spec §4.1.3 原文裁定 **T_expire = 4 小时** |
| 15 分钟调度 | ⚠ **未挂载**：实测 Windows `schtasks` 无相关任务（批次 A 自认「A.1 文档待补」）；WSL `crontab` 仅数据拉取×2 + 备份×1；`systemd --user list-timers` 0 个 |
| 演练要求 | ✓ 演练已实际执行，且演练 4 发现 stale `active_runs.json` 清理缺陷 → `b232e14` 修复——演练-修复闭环成立 |

### 偏离 1（须修正）：旗标过期 4 小时 → 实施 7 天

- closure spec §4.1.3 原文：「T_expire **4 小时**（覆盖一次常规部署；更长的维护须续期，touch 即可）」。
- 实施取 7 天（168 小时），**未附偏离理由**（批次 A 提交信息只写「7天过期机制」）。
- 该条款的风险论证正是「忘删旗标 → 自愈失效比不装看门狗更糟，因为故障不可见」；7 天使最坏暴露窗口放大 **42 倍**，实质弱化 fail-safe 方向。
- **处置**：改回 4 小时口径（常量改为小时制或等效换算）；需要长维护时用 `touch` 续期——spec 原文已有该机制，无须放大 T_expire。

### 偏离 2（须闭环）：调度未挂载，D4 生产未激活

- 看门狗代码 100% 就绪，但**无任何定时触发**——生产现状仍是「无自动自愈」（与回滚预案所述「当前生产状态」一致，不更糟，但 D4 未交付）。
- 调研 spec §2.2.1/§9 将落点改写为「WSL 内闭环（systemd timer 优先）」，与 closure spec 原文「Windows Task Scheduler 每 15 分钟调 WSL 跑一次」（Q3=(a)）**矛盾**；调研 spec §1「关键约束」的「不依赖 Windows Task Scheduler 以外的外部服务」表述有语病，放大了歧义。
- **处置**（宿主二选一）：
  - **选项 1（推荐）**：WSL 内 cron——`crontab` 已有 3 条存活任务证明该通道可靠，`*/15 * * * *` 一行即挂载，符合调研 spec 的 WSL 闭环诉求；
  - **选项 2**：Windows Task Scheduler——符合 closure spec 原裁定，抗 WSL 重启，但需 Windows 侧手工配置 + 补 A.1 文档。
  - 无论选哪个：挂载后须完成一次「杀 supervisor → 验证 ≈27 分钟内恢复」的实弹演练，D4 方可记「已交付」。

### 裁决理由

收编优于重写（已验证逻辑 + 避免双看门狗竞争重启），(a) 正确；S1-S4/熔断/告警/回滚路径实施质量良好。两项偏离均属可低成本修正的收尾缺口，不动摇裁定本身。
